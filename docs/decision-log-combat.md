**2026-08-18 (continuing the same session — Combat Encounter Tracker, two interaction-pattern fixes from the audit, both flagged the same tier of work: the condition picker's modal-to-dropdown conversion, and manual initiative reorder) — `dm.html`.**
**Condition picker — investigated the existing convention before writing anything new, per the explicit instruction to reuse it rather than invent one.** Read `.scc-picker-dropdown`/`.scc-picker-option` (the search-driven picker convention used by the combat-add box, loot-item search, etc.) and `.scc-history-panel`/`sccToggleHistory()` (a button-triggered anchored panel, closer in shape to this case since there's no text input involved — a plain click on a fixed set of options). Neither fits verbatim: `.scc-history-panel` is a single, static, always-in-DOM element toggled via a `.open` class, but the condition button is one of N per-row buttons living inside `#scc-initiative-list`, which gets fully `innerHTML`-replaced on nearly every state change — there's no stable single element to toggle a class on. `.scc-picker-dropdown`'s own `left:0;right:0` stretch-to-parent positioning assumes a `position:relative` wrapping container, which a body-appended, per-click-created panel doesn't have. Landed on a hybrid, reusing what genuinely transfers: `.scc-picker-option`'s row styling verbatim (real CSS `:hover` instead of the old modal's manual `onmouseover`/`onmouseout` JS), and the same body-append/remove-first lifecycle the OLD modal and the sibling Loot Award/Combat Summary popups already use in this exact file — but positioned via a live `getBoundingClientRect()` read against the clicked button rather than screen-centered, the same technique `sccPositionGlobalResults()` already established here for exactly this scenario (a fixed-position panel with no relative ancestor to anchor to). Colors/border/shadow/max-height copied directly from `.scc-picker-dropdown`'s real values rather than reusing the class name itself — reusing the class would have handed the panel's cleanup to this file's existing generic outside-click handler (`document.addEventListener('click', ...)` that empties `.scc-picker-dropdown.open` elements' innerHTML and removes the `.open` class, but does NOT remove the DOM node), which is correct for the *static* dropdowns it was built for but would leave an orphaned empty div in `document.body` for a create-on-click element like this one. Wrote a dedicated outside-click handler instead that calls `.remove()`, matching how every other body-appended overlay in this exact file's own neighborhood (Loot Award, Combat Summary) already fully removes itself rather than hiding-in-place.
**New behavior beyond a straight visual swap, matching how the rest of the app's pickers actually behave, not just how the old modal looked.** Clicking the same row's own "+ Condition" button a second time now toggles the dropdown closed instead of removing-then-immediately-recreating it (a real, if minor, functional gap in the old modal — it had no toggle-close at all, only an explicit "Close" button). A dedicated outside-click listener closes it too, mirroring the Session History panel's own established convention, adapted for a create-on-click element rather than a static one.
**A real correctness risk found while reasoning through the reorder feature below, fixed proactively rather than left as a known gap.** Both the new condition dropdown and the pre-existing Loot Award popup identify their combatant by a plain array index baked into their onclick handlers at the moment they're opened. Reordering (the new feature) or removing a combatant changes what that index actually refers to in `SCC_INITIATIVE` — a panel left open across such a change could apply a condition, a coin award, or an item award to whichever combatant now happens to occupy that slot, not the one the DM actually opened it for. Fixed at the single choke point both panels' lifecycles already pass through: `sccRenderInitiativeList()` now unconditionally closes both at the very top of every render. Verified this doesn't fight either panel's own "remove and reopen in place" refresh pattern (`sccAwardItem`/`sccUndoAwardItem`/`sccAwardCoins`/`sccAwardCoinsAll` all do this) by grepping for `sccRenderInitiativeList()` calls inside all four — none exist, so the new close-on-render only ever fires for renders triggered by something external to whichever panel is currently open (HP changes, Next Turn, Remove, or the new reorder), which is exactly the set of changes capable of invalidating a held index in the first place.
**Initiative reorder.** Small up/down arrow pair added per row, next to the initiative number — arrows only, matching the audit's own explicit recommendation that full drag-and-drop is more than this needs. New `sccMoveCombatant(idx, dir)` (`dir` is `-1` for up, `+1` for down) does one plain adjacent-slot array swap; the boundary arrows (first row's up, last row's down) render with the real HTML `disabled` attribute rather than a styled-only fake-disabled state, so there's no click event to even reach the handler at either edge. Deliberately does not touch either combatant's own rolled `initiative` number — only array order changes — so a manual reorder can freely diverge from the numbers instead of forcing them back in sync, which is the actual point per the audit's own framing (a Ready action interrupting the order, or a narrative tie-break, both need the *order* to move without a fake re-roll).
**`SCC_TURN_IDX` correctness — the part the ask flagged as most likely to have an edge case, worked through as a general proof rather than patched case-by-case.** A swap of two array slots only ever needs `SCC_TURN_IDX` updated when it currently equals one of the two slots involved, and if so, it becomes whichever of the two it *wasn't* — because a swap is symmetric, this single rule is provably sufficient for every real shape the instruction called out: the active combatant moving itself (its tracked index must follow it to the new slot), some other combatant swapping past the active one (the active combatant gets displaced into the mover's old slot, so the tracked index must follow *it*), and a swap that doesn't touch the active slot at all (nothing to update, since neither swapped position held it). Implemented as one small `if`/`else if`, not three separate code paths — the symmetry of a swap means one check covers all three cases correctly by construction, not by having enumerated and special-cased each one.
